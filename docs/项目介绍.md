# 项目介绍与面试表达

下面是基于本项目真实内容的介绍稿。使用前应亲自运行并能解释相关代码，避免把辅助生成成果表述成独立完成的工作经历。

## 简短介绍

这是一个 Python 与 pytest 测试练习项目，围绕手机号校验、密码校验和购物车总价计算设计了 45 个自动化测试场景。我通过参数化组织输入数据，通过 fixture 隔离购物车数据，并用异常断言检查无效输入。项目提供完整安装和运行说明、真实测试报告及失败排查示例，可以用于展示测试设计与项目整理能力。

## STAR 表达提纲

背景：已有多个 Python 小函数和 pytest 测试文件，需要把它们整理成可复现、可展示的项目。

任务：明确函数规则、整理源码与测试结构、补充边界场景，并提供别人能照着操作的安装说明和运行证据。

行动：保留已有测试，将模块放入 `src/qa_utils`，将测试放入 `tests`；明确金额使用半偶舍入；补充生成器输入、汇总后舍入和输入数据不被修改等场景；保存真实测试日志和报告。

结果：默认测试集共有 45 个场景。实际运行状态和独立副本验证结果以 `artifacts/summary.json`、`artifacts/reproduction.json` 和测试报告为准。

## 可能被追问的内容

| 问题 | 回答要点 |
| --- | --- |
| 45 个用例怎么计算？ | 参数化每组数据算一个独立场景，不等于 45 个测试函数。 |
| fixture 有什么价值？ | 每个用例得到一份新购物车，避免前一个测试修改数据影响后一个。 |
| 你实际补了哪些测试？ | 三个金额舍入场景、生成器输入、输入不被修改，共五个。 |
| 失败示例意味着项目有 bug 吗？ | 它故意使用错误预期，用于理解断言失败；正常测试集独立运行。 |
| 为什么没有 CI？ | 当前成果完成本地自动化、报告和复现验证；还没有配置或宣称远程自动运行。 |
| 通过测试能说明什么？ | 已执行的场景满足当前规则，不能证明没有其他缺陷。 |
